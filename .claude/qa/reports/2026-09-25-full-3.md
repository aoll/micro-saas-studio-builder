## Constats

### B-N1 · BO-05b étape 5 → 6 : « Suivant » bloqué par une fausse erreur de variable — BUG majeur

- **Étape** : 3.7 / 3.8 (bloque la navigation normale entre l'étape 5 « Génération » et l'étape 6 « Pricing »)
- **Référence** : specs/BO-05b-generation-publication.md › Acceptation (« Étape 5 : … une variable sans champ correspondant bloque l'étape ») · specs/BO-05a-formulaire.md (formulaire en étapes, « Suivant ») · docs/02 › BO-05 en détail
- **Repro** :
  1. Se connecter en admin, ouvrir `/admin/products/new`.
  2. Coller `fixtures/bio-instagram.config.json` dans « Coller une configuration JSON », cliquer « Importer ».
  3. Cliquer « Suivant » trois fois pour atteindre l'étape 5 (Identité → Thème → Landing & SEO → Champs de l'outil → Génération), **sans rien modifier**.
  4. À l'étape 5, cliquer « Suivant ».
- **Attendu** : passage à l'étape 6 (Pricing), puisque le template importé (`{{niche}}`, `{{highlights}}`, `{{tone}}`) correspond exactement aux 3 champs importés (`niche`, `highlights`, `tone`).
- **Observé** : l'étape reste bloquée à 5, avec l'erreur « Variable {{niche}} sans champ correspondant » sous le champ Template de prompt — alors que `niche` est un champ bien configuré. Reproduit deux fois avec la config `bio-instagram` intacte (aucune modification de ma part), donc systématique pour tout produit réel : la validation compare toujours le template à un champ factice `sujet` au lieu des vrais champs de l'étape 4.
- **Cause (lue dans le code, non corrigée)** : `app/(backoffice)/admin/products/_components/product-form/product-form.tsx`, fonction `stepPatch(step, draft)` — le `case 5` ne renvoie que `{ generation: draft.generation }`, jamais `inputs`. `handleNext()` appelle `validateStep(5, stepPatch(5, draft))` (`validation.ts`), qui fusionne ce patch sur `VALID_BASELINE` — un config factice dont `inputs` vaut `[{ key: "sujet", … }]` (`validation.ts:44-49`). La vérification croisée `productConfigSchema`'s `superRefine` (`lib/schemas/product-config.ts:136-144`) compare alors le vrai template aux champs du produit **factice** (« sujet »), jamais aux vrais champs du produit en cours de création, donc toute variable réelle (`niche`, `highlights`, `tone`…) est signalée comme manquante. Le contournement existe : cliquer directement l'onglet « 6. Pricing » dans la navigation latérale (`StepNav`, qui appelle `setCurrentStep` sans validation) fait avancer sans problème, et « Enregistrer » (Server Action `saveProduct`, qui valide le config complet réel) fonctionne aussi normalement — vérifié : la publication de BioInsta (3.9) et l'édition (6bis) ont abouti sans cet obstacle en utilisant ces deux chemins.
- **Preuve** : capture `3.7-suivant-faux-blocage.png` (étape 5, template intact, erreur affichée) ; `network requests` confirme qu'aucune requête serveur n'accompagne le blocage (validation 100 % client) ; relecture de `product-form.tsx:41-58` et `validation.ts:32-49,95-102`.
- **Fichiers de la route** : `app/(backoffice)/admin/products/_components/product-form/product-form.tsx` (`stepPatch`), `app/(backoffice)/admin/products/_components/product-form/validation.ts` (`VALID_BASELINE`, `validateStep`)
- **Serveur ou UI** : UI (validation client uniquement)
- **Sévérité** : majeur — le bouton « Suivant », chemin documenté et attendu du formulaire en étapes (docs/02 › BO-05 en détail, script de démo docs/01), échoue systématiquement à l'étape 5 pour toute configuration réelle ; il existe un contournement (onglets de navigation, ou « Enregistrer »), donc pas de perte de données ni blocage total, d'où majeur et non bloquant.

### B-N2 · BO-05a étape 4 : une clé de champ dupliquée déclenche une erreur console React — BUG mineur

- **Étape** : 3.6
- **Référence** : specs/BO-05a-formulaire.md › Acceptation (« clés uniques ») · docs/02 › BO-05 en détail (étape 4)
- **Repro** :
  1. `/admin/products/new`, importer `fixtures/bio-instagram.config.json`, aller à l'étape 4 « Champs de l'outil ».
  2. Modifier la clé du 2ᵉ champ (`highlights`) pour la faire correspondre à celle du 1ᵉʳ champ (`niche`).
  3. Observer la console du navigateur.
- **Attendu** : le message « Clé déjà utilisée » s'affiche sous le champ concerné (comportement fonctionnel correct, vérifié PASS), sans erreur React dans la console.
- **Observé** : en plus du message de validation correct, la console affiche deux fois `Encountered two children with the same key, "niche". Keys should be unique so that components maintain their identity across updates…`, provenant de `generation-step.tsx:89` (boutons `{{variable}}` cliquables) et `prompt-tester.tsx:47` (champs de l'échantillon), qui utilisent tous deux `key={input.key}` sur la liste des champs — non défendu contre les doublons transitoires pendant la saisie.
- **Preuve** : sortie de `agent-browser console` après la saisie, reproduite une seconde fois sur un contexte navigateur neuf (session `qa-full-3f`), isolée de tout autre test.
- **Fichiers de la route** : `app/(backoffice)/admin/products/_components/product-form/generation-step.tsx`, `app/(backoffice)/admin/products/_components/product-form/prompt-tester.tsx`
- **Serveur ou UI** : UI (React, clé de liste)
- **Sévérité** : mineur — la validation fonctionnelle bloque correctement l'étape (« Clé déjà utilisée », vérifié), aucune donnée n'est perdue ; c'est un défaut d'hygiène React (avertissement console) visible pendant une opération normale du formulaire.
