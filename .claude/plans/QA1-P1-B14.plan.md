# Implementation Plan: QA1-P1-B14 · Plus d'erreur Cache Components sur l'outil et le paiement

## Overview

Two independent Cache Components violations, both cosmetic (dev-only, HTTP 200 either way) but real per docs/04's rendering contract: (1) `lib/dal/session.ts`'s `getSession()` triggers a "sync IO" (`new Date()`) error during prerendering, reported wherever it's reached inside a `<Suspense>` boundary (the shared `HeaderBalance`, hence on `/[app]/tool` and on the checkout modal too); (2) `[app]/checkout/[packId]/page.tsx` awaits `params` at the top of the component, outside any `<Suspense>`, which Cache Components flags categorically. Both fixes are exactly the patterns Next 16.3's own migration guide documents, applied without touching `getSession()`'s signature.

## Requirements (spec `Acceptation`)

- `/{slug}/tool` connecté, `/{slug}/checkout/[packId]` en page et en modale : aucune erreur « unstable value new Date() » ni « URL data outside of `<Suspense>` » en console, dans `get_errors` ni dans le journal du serveur.
- Le shell reste statique (docs/04) : les données de session restent sous `<Suspense>`, jamais mises en cache.

## Root cause analysis

### 1. `new Date()` while prerendering — `lib/dal/session.ts:14`

```ts
export const getSession = cache(async (): Promise<Session | null> => {
  const session = await auth.api.getSession({ headers: await headers() });
  return session ?? null;
});
```

`HeaderBalance` (`components/product/header-balance.tsx`) is already correctly wrapped in `<Suspense>` by the shared layout (`app/(products)/[app]/layout.tsx:104-106`), and `getSession()` already awaits `headers()`, a legitimate Next.js Request-time API — on paper that alone should be the suspension point (`io.md` › "When you don't need `io()`"). In practice the QA capture shows the crash happens anyway, deep inside `auth.api.getSession()` (Better Auth's own session/expiry check calls `new Date()` internally). Per `migrating-to-cache-components.md` › *Adopting incrementally* / *Common pitfalls*, sync-IO calls (`new Date()`, `Math.random()`, `crypto.randomUUID()`) are **not** cleared just by being reached after a Request-time API or inside a `<Suspense>` boundary — Next's dev validation pass can still reach and flag them (a known class of issue when a 3rd-party library performs sync IO after its own internal await chain, since the "postpone" signal from `headers()` isn't guaranteed to unwind through arbitrary library code). The documented fix (`io.md`, `migrating-to-cache-components.md` › *Adopting incrementally* step 3) is to call `io()` (preferred over `connection()`: it doesn't block prefetching, and `getSession`'s result should stay prefetchable per-session, `authentication-with-cache-components.md` › Step 6) **before** the code that performs sync IO, so Next treats everything after that point as excluded from the static shell regardless of what the library does internally.

Fix — inside `getSession()`'s body only, contract-safe (`Contrat: getSession() garde sa signature`):

```ts
import { io } from "next/cache";
...
export const getSession = cache(async (): Promise<Session | null> => {
  await io();
  const session = await auth.api.getSession({ headers: await headers() });
  return session ?? null;
});
```

Placed as the very first statement, ahead of `headers()` too, so the fix doesn't depend on `headers()`'s own deferral behaving correctly. `io()` resolves immediately at request time and inside cached scopes (`io.md` › Reference), so this is a no-op in production and in every other DAL call site of `getSession()` (Server Actions in `checkout/_actions.ts`, Route Handlers `api/generate/route.ts` and `signup/complete/route.ts`, `admin/ops/page.tsx`, `history-list.tsx`, `account-content.tsx`, `admin-sidebar.tsx`) — none of those need their own change, since this is the single low-level primitive all of them go through (confirmed by grep: every `getSession()` caller in the repo imports it from `lib/dal/session.ts`). `getBalance()` (`lib/dal/credits.ts`) also calls `getSession()` again internally via `assertReadableBalance`; React's `cache()` memoizes per request, so this is a second hit on the same fixed function, not a second bug.

No change needed in `components/product/header-balance.tsx` or `tool/page.tsx` themselves — they're already structured correctly (Suspense boundary in place, no top-level session/cookie read in the page). They stay in `Périmètre` for their regression tests only.

### 2. "URL data … outside of `<Suspense>`" — `checkout/[packId]/page.tsx:21`

```tsx
export default async function CheckoutPage({ params }: PageProps<"/[app]/checkout/[packId]">) {
  const { app: slug, packId } = await params;   // ← awaited at the top, outside <Suspense>
  ...
}
```

Per `migrating-to-cache-components.md` › *`generateStaticParams` and `dynamicParams`* › *Await `params` inside `<Suspense>`*, this is flagged categorically under Cache Components, regardless of whether `generateStaticParams` already enumerates every concrete `packId` (it does here, from `product.pricing.packs`) — the fix is always to push the `params` promise, unawaited, into a `<Suspense>`-wrapped child, exactly the pattern already used one route over in `history/page.tsx` (`searchParams` forwarded unawaited into `<HistoryList searchParams={searchParams} />` inside `<Suspense>`).

Fix:

```tsx
import { Suspense } from "react";
...
export default function CheckoutPage({ params }: PageProps<"/[app]/checkout/[packId]">) {
  return (
    <Suspense fallback={<CheckoutSkeleton />}>
      <CheckoutContent params={params} />
    </Suspense>
  );
}

async function CheckoutContent({ params }: Pick<PageProps<"/[app]/checkout/[packId]">, "params">) {
  const { app: slug, packId } = await params;
  const product = await getProduct(slug);
  if (!product) notFound();
  const pack = product.pricing.packs.find((candidate) => candidate.id === packId);
  if (!pack) notFound();
  return (
    <CheckoutFlow variant="page" slug={product.slug} productName={product.name} pack={pack}
      costPerGeneration={product.pricing.costPerGeneration} />
  );
}
```

`generateStaticParams` is untouched (build-time export, unrelated to this runtime structure). `getProduct()` is already `'use cache'` (`lib/dal/products.ts`), so once warm this resolves near-instantly behind the boundary; a small `CheckoutSkeleton` (mirroring `BalanceBadgeSkeleton`'s pattern in `components/product/balance.tsx`) is the fallback.

## Overlap with B3 (flagged per the task's instruction)

- **Direct file conflict**: `checkout/[packId]/page.tsx` is in *both* specs' `Périmètre`. B3's own spec text explicitly excludes "l'erreur Cache Components de checkout/[packId]/page.tsx" from its scope, and B14 explicitly depends on B3 merging first (`Dépend de: QA1-P1-B3-paiement-pricing`) — confirming the split is deliberate: B3 may still touch this file for its own bug (the confirmation-then-full-reload issue, whose QA capture shows the *exact same* "URL data during prerendering or a navigation" console message — B3's behavioral symptom and B14's structural violation are plausibly the same root cause manifesting two ways), B14 layers the Suspense/params restructuring on top of whatever B3 leaves there.
- **Action for the TDD loop**: start by re-reading the post-B3 version of `checkout/[packId]/page.tsx` before writing any test — B3 may have already partially restructured it (e.g. around `refresh()` handling or the client-side confirmation state), and the `CheckoutContent`/`Suspense` split must be grafted onto that version, not onto the version read during this planning pass.
- **Modal is out of `Périmètre` here.** `@modal/(.)checkout/[packId]/page.tsx` has the identical `await params` pattern today but belongs entirely to B3 (`[app]/@modal/(.)checkout/**` is in B3's `Périmètre`, not B14's). **Risk**: the spec's own acceptance bullet says "`/{slug}/checkout/[packId]` en page et en modale" — if B3 does not independently restructure the modal the same way, B14 cannot close that half of the acceptance criterion without stepping outside its `Périmètre`. Flag this explicitly to the orchestrator/human once B3 has merged: check the modal for the same console error before calling B14 done, and if it's still present, escalate for either a `Périmètre` widening or a fast-follow spec — do not silently fix it out of scope.
- **`checkout/_actions.ts`, `checkout/_components/**`**: untouched by B14 either way (not in its `Périmètre`); no risk of edit conflict there.

## Risks & Mitigations

- **Risk**: `io()` inside `getSession()` changes behavior somewhere unexpected (e.g. a currently-passing test or a route that isn't actually inside a `<Suspense>` boundary today, like `admin/ops/page.tsx` or the Route Handlers).
  - Mitigation: `io()` resolves immediately in every non-prerendering context (Server Actions, Route Handlers, real requests, Vitest) per `io.md`'s own Reference table — verify with `pnpm test` after step 2 that the full suite (not just `session.test.ts`) stays green before moving to Phase 2.
- **Risk**: File conflict / stale assumptions with B3 on `checkout/[packId]/page.tsx` (see "Overlap with B3").
  - Mitigation: re-read the file fresh right after B3 merges, before writing step 4's test; keep the new skeleton component inside `checkout/[packId]`'s own directory rather than the shared `checkout/_components/`.
  - Mitigation: don't attempt to fix the modal; escalate if it's still broken after B3 merges.
- **Risk**: The Vitest tests (steps 1, 4) verify the *mechanism* (call order, element structure) but not Next's actual prerendering validator — a subtly wrong fix could still pass Vitest and fail in the real dev server.
  - Mitigation: steps 3 and 6 are mandatory, not optional, and their output goes in the PR description; `/verify`'s spec-conformance check should re-run them too.
