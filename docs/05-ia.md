# L'IA dans la démo

## Verdict : AI SDK ou SDK Anthropic ?

**AI SDK 7 (Vercel), avec les modèles Anthropic par défaut.** Pour un seul produit branché sur Claude, le SDK Anthropic direct suffirait. Mais la démo est un **studio multi-produits dont le modèle est un champ de la config** : c'est exactement le cas pour lequel l'AI SDK existe.

| Critère | AI SDK 7 | SDK Anthropic direct |
| --- | --- | --- |
| Modèle choisi dans le backoffice | Une chaîne (`anthropic/claude-…`, `openai/…`), même code pour tous | Claude uniquement |
| Produits à sortie **image** (`outputType: image`) | `generateImage` avec OpenAI, Google, Fal… | Impossible : Claude ne génère pas d'images |
| Streaming vers l'UI | `streamText` → `toUIMessageStreamResponse()` + `useCompletion` / `useObject` | Flux SSE à relayer et parser soi-même |
| Sortie structurée (ex. 3 bios) | `Output.object({ schema })` avec Zod, objets partiels streamés | Possible, plus de code |
| Coût par génération | `usage` : `inputTokens`, `outputTokens`, `cachedInputTokens`, dans `onFinish` | Disponible, format propre à Anthropic |
| Fonctions spécifiques Claude | Prompt caching, thinking, structured outputs, PDF via `providerOptions` | Tout, dès la sortie |
| Observabilité | `@ai-sdk/otel` (conventions GenAI) | À instrumenter |
| Contraintes | Node 22 minimum, ESM obligatoire | Aucune particulière |

**Pourquoi c'est aussi le bon choix pour la candidature** : Dotworld propose déjà un produit de « design par IA » avec un système de crédits, donc des produits à sortie image. Montrer un studio où l'on choisit le modèle produit par produit, et où un générateur d'images se configure comme un générateur de texte, parle directement à leur métier. L'AI SDK est aussi l'outil standard de l'écosystème Next.js qu'ils utilisent.

**Ce qu'on perd** : une couche d'abstraction de plus, et un léger décalage possible quand Anthropic sort une nouvelle fonctionnalité. Pour ce que fait la démo (texte streamé, sortie structurée, prompt caching), le provider `@ai-sdk/anthropic` couvre tout.

## L'AI SDK dans la démo

Tout appel LLM passe par **un seul module**, `lib/ai/generate.ts`, qui lit la config du produit et choisit la bonne fonction selon `outputType`. Le Route Handler `api/generate` ne fait que l'appeler et renvoyer le flux.

| Besoin | Fonction AI SDK | Où |
| --- | --- | --- |
| Génération de texte streamée | `streamText` + `toUIMessageStreamResponse()` / `toTextStreamResponse()` | `api/generate` (SA-02) |
| Plusieurs propositions typées (3 bios, 5 noms de marque) | `streamText` + `Output.object({ schema })`, objets partiels | `api/generate` |
| Produits à sortie image | `generateImage` | `api/generate` |
| « Tester le prompt » dans le backoffice | `generateText`, sans débit | Server Action `testPrompt` (BO-05) |
| Affichage progressif côté client | `useCompletion` (texte), `useObject` (JSON streamé) | Outil SA-02 |
| Coût IA par génération | `usage` dans `onFinish` × prix du modèle | Table `generations` |
| Remboursement si échec | `onError` → `credits.refund()` | DAL |
| Traces | `@ai-sdk/otel` | `instrumentation.ts` |

```ts
// lib/ai/generate.ts (extrait)
export function streamGeneration({ product, inputs, generationId }: Args) {
  return streamText({
    model: product.generation.model,                 // chaîne issue de la config
    system: product.generation.systemPrompt,         // partie stable : mise en cache
    prompt: renderTemplate(product.generation.promptTemplate, inputs),
    output: product.generation.schema ? Output.object({ schema: toZod(product.generation.schema) }) : undefined,
    providerOptions: { anthropic: { cacheControl: { type: 'ephemeral' } } },
    onFinish: ({ usage }) => after(() => saveGeneration(generationId, usage)),
    onError: () => after(() => credits.refund(generationId)),
  })
}
```

**Deux détails qui comptent pour un studio**

- **Prompt caching** : le prompt système d'un produit est identique pour tous ses utilisateurs. Le marquer en cache via `providerOptions` réduit le coût en tokens d'entrée dès qu'il dépasse le minimum requis par le modèle (1 024 à 4 096 tokens selon le modèle). `cachedInputTokens` le rend visible dans le backoffice. Attention : un prompt système court (\~800 tokens) reste sous ce seuil ; le caching ne joue qu'avec des prompts enrichis (exemples few-shot, consignes détaillées).
- **Le coût IA devient une colonne de la fiche produit** : `usage` est lu à chaque génération, multiplié par le prix du modèle et stocké. La marge par génération (BO-03) en découle directement.

**À vérifier au démarrage** : AI SDK 7 exige **Node 22** et **ESM** (`"type": "module"`). Next.js 16.3 est compatible ; le runtime de déploiement doit l'être aussi.

## AI Gateway

**À brancher dès la v1.** L'AI Gateway est ce qui permet à l'AI SDK d'accepter un modèle sous forme de simple chaîne (`'anthropic/…'`, `'openai/…'`) : une seule clé (`AI_GATEWAY_API_KEY`, ou OIDC sur Vercel) donne accès à tous les fournisseurs. Sans elle, il faut importer et configurer chaque provider séparément.

| Ce qu'apporte le Gateway | Usage dans la démo |
| --- | --- |
| **Zéro marge** sur le prix des tokens, y compris avec ses propres clés (BYOK) | Le coût affiché dans le backoffice est le vrai coût fournisseur |
| **Fallback de modèles** (`providerOptions.gateway.models`) et ordre des fournisseurs (`order`) | Un champ « modèle de secours » dans la config produit ; `modelAttempts` dit quel modèle a répondu |
| **Logs** : modèle, fournisseur, latence, tokens, coût, statut de chaque requête | Contrôle croisé avec la table `generations` |
| **Budgets** par équipe, projet, clé d'API ou membre | Un plafond de dépense pour la démo publique : aucune mauvaise surprise si l'URL circule |
| Palier **gratuit** avec crédits mensuels (sous-ensemble de modèles, limites de débit plus basses) | Suffisant pour développer ; quelques euros de crédits pour la démo |
| Fonctionne **hors de Vercel** avec une clé d'API | Reste valable si la démo tourne en Docker sur Fly.io |

```ts
streamText({
  model: product.generation.model,                        // ex. 'anthropic/claude-…'
  providerOptions: {
    gateway: { models: product.generation.fallbackModels }, // essayés dans l'ordre si le principal échoue
  },
  // …
})
```

**À savoir**

- Les budgets sont des **plafonds souples** et ne couvrent que la dépense facturée par le Gateway, pas celle faite avec ses propres clés. Le rate limit de la démo (dans Postgres) reste nécessaire.
- « Custom Reporting » (tags et IDs utilisateur par requête) est payant à l'usage. Inutile ici : la table `generations` fait déjà ce travail.

## Sûreté des entrées et des sorties

Les champs saisis par l'utilisateur sont injectés dans le prompt, et la sortie s'affiche en direct, parfois devant un recruteur. **Quatre garde-fous suffisent à cette échelle**, sans service de modération externe.

| Risque | Garde-fou | Où |
| --- | --- | --- |
| Injection de prompt (« ignore tes consignes et… ») | Les entrées sont placées dans des balises délimitées du prompt et décrites comme des données ; le prompt système rappelle la tâche unique du produit | Template de prompt |
| Entrées abusives ou très longues | Longueur maximale par champ et valeurs de select validées par le schéma Zod du produit | Route Handler `api/generate` |
| Sortie déplacée (insultes, contenu choquant) | Consignes de sûreté communes à tous les produits, ajoutées au prompt système par le socle et non modifiables dans la config | `lib/ai/generate.ts` |
| Sortie hors format | Sortie structurée (`Output.object`) validée par Zod ; en cas d'échec, remboursement du crédit | DAL crédits |

**Données personnelles** : la démo collecte des emails (comptes) et des textes saisis (générations). Une page de mentions et de confidentialité d'une dizaine de lignes suffit : finalité (démonstration), durée (supprimé à chaque remise à zéro), contact. Les entrées ne servent pas à entraîner de modèle.

**Traçabilité** : chaque génération enregistre la version de config qui l'a produite (`product_version`). On peut ainsi relier une variation de conversion ou de coût à un changement de prompt.

## Consommation de tokens : mock et seed

**Avec la stratégie ci-dessous, la démo complète coûte moins de 2 $ d'API** (répétitions, entretiens et URL publique compris). Une génération coûte une fraction de centime ; ce qui fait monter la facture, ce sont les appels inutiles en développement et en test.

**Coût unitaire** (tarifs Anthropic au 23 septembre 2026 : Haiku 4.5 à 1 $ / 5 $ par million de tokens en entrée / sortie, Sonnet 5 à 2 $ / 10 $)

| Génération | Tokens entrée / sortie | Haiku 4.5 | Sonnet 5 |
| --- | --- | --- | --- |
| 3 bios Instagram, noms de marque | \~1 000 / \~300 | 0,25 centime | 0,5 centime |
| Lettre de motivation, description produit | \~1 000 / \~600 | 0,4 centime | 0,8 centime |
| 10 lettres + 10 fiches Insta | \~20 000 / \~9 000 | \~6,5 centimes | \~13 centimes |

**Où part le budget, avant et après**

| Usage | Sans stratégie | Avec mock, fixtures et Haiku |
| --- | --- | --- |
| Tests automatiques et développement | \~500 appels réels | 0 appel (mock) ; quelques dizaines pour valider les prompts |
| Seed de la base | \~100 appels à chaque reset | 0 (fixtures committées) |
| Répétitions et entretiens | \~200 appels | \~200 appels, en Haiku |
| URL publique | \~250 appels | \~250 appels, plafonnés (rate limit, BotID, budget Gateway) |
| **Total** | **\~6 $ en Sonnet** | **< 2 $** |

### Stratégie de mock

Un seul point d'entrée décide du modèle réellement appelé : `lib/ai/model.ts`. Tout le reste du code (`streamGeneration`, `testPrompt`) ignore s'il parle à un vrai modèle ou à un mock.

```ts
// lib/ai/model.ts
import { MockLanguageModelV4 } from 'ai/test'
import { simulateReadableStream } from 'ai'

export function resolveModel(modelId: string, slug: string) {
  if (process.env.AI_MODE === 'mock') return mockModelFor(slug)  // tests, dev par défaut    
  return modelId                                               // chaîne AI Gateway en mode 'live'
}

function mockModelFor(slug: string) {
  const fixture = fixtures[slug]                               // sortie réaliste pour ce produit
  return new MockLanguageModelV4({
    doStream: async () => ({
      stream: simulateReadableStream({
        chunkDelayInMs: 30,                                    // l'UI streame comme en vrai
        chunks: [...toTextChunks(fixture.text), finishChunk(fixture.usage)],
      }),
    }),
  })
}
```

| Mode `AI_MODE` | Où | Comportement |
| --- | --- | --- |
| `mock` | Tests Vitest et Playwright, dev par défaut | `MockLanguageModelV4` + `simulateReadableStream` : sortie de la fixture du produit, streamée avec un délai, `usage` réaliste. Zéro token. |
| `live` | Démo, URL publique, validation d'un prompt | Vrai modèle via l'AI Gateway |

**Ce que le mock permet de tester sans dépenser** :

- tout le parcours de crédits : débit, `usage` → coût IA stocké, historique ;
- le remboursement, avec un mock qui lève une erreur au milieu du flux ;
- le streaming dans l'UI, et les tests `instant()` de Playwright ;
- la sortie structurée (`Output.object`), avec une fixture JSON conforme au schéma Zod du produit.

### Stratégie de seed

Les fixtures sont **générées une seule fois avec le vrai modèle, puis committées**. Elles servent à la fois au seed de la base et au mock.

1. `pnpm fixtures:record` : pour chaque produit seedé, 5 à 10 vraies générations en Haiku (entrées variées), enregistrées avec leur `usage` dans `fixtures/{slug}.json`. Coût total : quelques centimes, une fois.
2. `pnpm db:seed` : crée les produits, thèmes et utilisateurs, insère les historiques de générations à partir des fixtures, et simule 30 jours d'`events` par calcul. Aucun appel au modèle : on peut réinitialiser la base autant de fois qu'on veut.
3. On relance `fixtures:record` seulement quand le template de prompt d'un produit seedé change.

**En démo live**, seul le produit créé devant le recruteur (« Générateur de bio Instagram ») fait de vrais appels : quelques générations, moins d'un centime.

**Garde-fous** : Haiku par défaut pour les produits simples, Sonnet réservé à un produit « premium » ; budget plafonné sur l'AI Gateway ; rate limit et BotID sur la génération.

Ces chiffres ne comptent pas le développement avec Claude Code, bien plus volumineux, qui passe par l'abonnement ou la clé Claude Code. Le coût d'un produit à sortie image n'est pas estimé ici et dépasse nettement celui du texte : à vérifier avant de l'ajouter.

## Ce qu'on retient pour la v1

**Dans la v1**

- [ ] AI SDK 7 comme unique couche d'appel LLM (`streamText`, `Output.object`, `generateImage`, `generateText`), modèles Anthropic par défaut
- [ ] AI Gateway : modèle et modèle de secours dans la config produit, budget plafonné pour la démo publique
- [ ] Coût IA calculé depuis `usage` et stocké par génération ; prompt caching sur le prompt système
- [ ] Rate limit sur la génération et le test de prompt ; \`AI\_MODE=mock\` par défaut, fixtures committées pour le seed

**Bonus, dans l'ordre**

1. Produit à sortie image (`generateImage`) parmi les produits seedés
2. Traces OpenTelemetry avec `@ai-sdk/otel`

**Hors périmètre** : le SDK Anthropic direct, les agents et outils (`HarnessAgent`, `WorkflowAgent`), le temps réel et la vidéo.

L'AI SDK et l'AI Gateway (avec une clé d'API) fonctionnent quel que soit l'hébergeur. Les briques liées à la plateforme sont dans l'onglet Vercel.
